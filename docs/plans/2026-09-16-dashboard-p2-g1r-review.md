# Dashboard P2 G1R review

Reviewed `2026-09-16-dashboard-p2-contract.md` against PR #80 head `a6716dcf2c585ac3a2e19d4317a56af6ba3ba741` and the current workspace, process, provider, broker, receipt, and approval implementations.

## Judgment

**APPROVE — `READY_FOR_P2_BUILDER`.** The amended contract is implementable as a bounded goal-to-candidate service and addresses the current proposal-only runner rather than relabelling it. P2 completion means a sealed, evidence-bound candidate in an isolated workspace with a successful `structural-v1` check. It does not mean the original project was modified, tests passed, or a change was accepted or applied.

No live provider, credential, paid request, generated candidate, or primary-tree application was exercised by this review. Those remain implementation and validation evidence for Builder/G2A.

## Findings

1. **The execution mechanism is real and bounded.** Current live dispatch forbids tools, file access, and commands and runs Claude with empty tools in plan mode (`adapters/live_provider.py:253-303`); its builder schema is only a status and a 120-character proposal (`domain/stage_response.py:7-26,39-58`). The P2 contract instead defines a task-specific provider adapter that receives a canonical scoped source bundle and returns actual `create`/`replace` UTF-8 contents under `torq-candidate-output-v1` (`dashboard-p2-contract.md:55-63`). TORQ validates identities and writes the candidate; the provider never selects paths outside the reviewed plan or supplies executable commands.

2. **Isolation does not rely on the existing copy sandbox unchanged.** `WorkspaceManager.create` currently copies the complete primary with links preserved and uses an existence lock (`safety/workspace.py:93-116`), which is insufficient for provider-bound source handling and crash-safe cross-process ownership. The approved contract requires disjoint source/state/work/runtime roots, owner-only bounded snapshots of explicitly scoped ordinary files, link/reparse/hardlink/device/ADS/case/protected-path rejection, finite traversal/byte limits, and source identity checks before dispatch and readiness (`dashboard-p2-contract.md:26-35,37-45`). Process ownership is correctly not described as an OS filesystem sandbox.

3. **Start persistence and replay have executable invariants.** Draft revisions use server-side CAS; a reviewed plan binds goal revision, project, source identity, exact path scope, provider/model, checker, and limits; Start is keyed by a canonical request digest and durable reservation created before dispatch (`dashboard-p2-contract.md:26-31`). One installation state root owns idempotency and a kernel-held lifetime lock. Same-key/same-body replay returns the existing task, changed-body replay conflicts, and restart recovery never silently re-dispatches a provider.

4. **Candidate readiness is a semantic evidence verdict.** The service reuses the existing broker/certificate/receipt envelope but discriminates `task_contract=torq-candidate-task-v1` inside an outer coordinator `audit` event. Strict closed payload checks run at append and independent verification, and a sequence validator enforces one task identity, ordered start/generated/check events, exactly one terminal, no post-terminal evidence, and terminal-before-seal (`dashboard-p2-contract.md:47-55`). Generic signed audit events cannot project readiness. `candidate_ready` must link the accepted plan, base/input identities, exact encrypted candidate bundle, raw and cipher hashes, checker identity/result, zero exit, complete output, confirmed process-tree termination, and unchanged source recheck. Projection derives from verified receipts and decrypted artifacts rather than the mutable task cache.

5. **Exact candidate bytes survive the redaction boundary.** Existing `ReceiptChain.write_artifact` scans and may transform text before encrypting it (`safety/receipts.py:1485-1505`). The contract avoids a false exactness claim by requiring source and output scans to return unchanged text, hard-rejecting redaction findings, hashing raw UTF-8 bytes before persistence, and reading the encrypted artifact back to prove byte equality (`dashboard-p2-contract.md:37-39`). Binary, delete, rename, and empty-directory changes remain outside P2 v1.

6. **Checks cannot become arbitrary model-controlled execution.** The only initial policy is `structural-v1`; the server constructs the fixed `trusted_python -I -S packaged_helper` argv, pins and rechecks helper bytes, strips provider credentials, and parses supported Python/JSON/text without importing or executing candidate code (`dashboard-p2-contract.md:63-65`). Candidate readiness requires an actual zero exit, bounded complete output, and confirmed empty process-tree termination. The UI must call this syntax/format validation, not unit tests or “all checks passed.”

7. **P2 and P3 are cleanly separated.** `candidate_ready` seals an immutable P2 result. P3 must open a separate review/apply transaction bound to that result and may not use the current v2 approval resolver, whose approval path terminalizes as completed without applying a governed change (`application/orchestrator.py:1242-1300`; `docs/design/governed-change-transaction.md:18-23,43-60`). P2 exposes no Accept action and performs no source-project write.

## Builder and G2A release gate

Builder must satisfy the production-coordinator integration oracle with a real owned fixture-provider process, real packaged checker subprocess, and real broker: authenticated draft/plan/start, actual candidate file changes, unchanged source hashes, exact artifact readback, signed semantic readiness, idempotent replay, and restart recovery. Production provider command wiring must be tested separately. G2A must independently exercise the negative matrix in the contract, full affected and repository regressions, lint/type/package checks, and an installed-wheel browser flow. Fixture execution proves production plumbing but is not live-vendor validation; any live-provider claim requires an actually authorized and observed request.
