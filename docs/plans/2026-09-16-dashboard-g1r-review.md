# PR 80 G1R review

Reviewed PR #80 at exact head `a6716dcf2c585ac3a2e19d4317a56af6ba3ba741` against the repository implementation and the amended G1D build contract. This is a source and contract review. Reported CI and local fixture checks are baseline evidence only; no live provider, credential, paid request, file-editing agent, or governed change application was validated by this review.

## Judgment

- **Full goal-to-governed-build plan: REVISE.** The product direction is sound, but P2/P3 are not builder-ready as an implementation promise. The current live runtime is a tool-disabled decision pipeline and the governed change transaction remains design-only.
- **Amended bounded P0/P1 contract: APPROVE.** Builder handoff is ready for the friendly workspace, truthful capability metadata, root diagnostics, provider-driven attachment controls, session-scoped drafts, legacy Fleet preservation, and the specified UI/test work in `2026-09-16-dashboard-g1d-build-contract.md`.
- **Builder handoff scope:** `READY_FOR_BOUNDED_P0_P1`. It does not include task creation, file edits, command execution, diff/check review, acceptance/application, or build-tool parity.

## Numbered findings

1. **Blocking contradiction resolved by scope, not by existing runtime.** The main plan says P2 will edit files and run commands through existing governed services (`2026-09-16-dashboard-ux-plan.md:5-16,243-257`). `RunController.start` only invokes the governed orchestrator (`application/run_command.py:70-155`); its live dispatcher explicitly says not to use tools, access files, or execute commands and invokes Claude with `--tools ""` and plan mode (`adapters/live_provider.py:253-303`). The live runtime also creates an isolated temporary working directory outside the target roots (`application/live_runtime.py:49-63,164-175`). The builder response contract is only a closed `status` plus a proposal string of at most 120 characters (`domain/stage_response.py:7-26,39-58`). Therefore existing run creation cannot meet the P2 exit gate.

2. **Governed application and review artifacts are missing executable contracts.** The authoritative transaction design says it is design-only and describes today's approval-without-application gap (`docs/design/governed-change-transaction.md:1-23,43-60`). The main plan's run-start snapshot, run-bound diff, check command/exit evidence, accepted revision, and governed application semantics (`2026-09-16-dashboard-ux-plan.md:227-258`) require a separately reviewed implementation before P2/P3 can ship. The bounded contract correctly keeps `can_start_task=false`, exposes execution as unsupported, and forbids decorative Build/Accept controls (`2026-09-16-dashboard-g1d-build-contract.md:18-23`).

3. **The bounded server contract now preserves the per-run trust boundary.** The existing HTTP server owns one projector and rejects controller roots that differ from that projector (`interfaces/fleet_http.py:301-338`); it currently exposes only Fleet/chat reads and Fleet/chat/context/action/recovery mutations (`interfaces/fleet_http.py:445-494,625-669`). The approved increment adds authenticated read-only workspace metadata without mutable projector rebinding, requires bounded immediate-child discovery for collections, and preflights root classification plus receipt/certificate trust before any key-store or chat-journal mutation (`2026-09-16-dashboard-g1d-build-contract.md:20-24,33-39`). This is the correct pragmatic boundary for a useful dashboard slice.

4. **Draft and continuation semantics are now executable and honest.** The child Claude process disables provider session persistence (`adapters/chat_provider.py:48-75`), while TORQ reconstructs bounded continuation from verified submitted/completed chat evidence (`application/chat_runtime.py:618-635`). The approved contract therefore treats this as discussion continuation only, keeps active/unavailable composers editable, forbids queued or automatic sends, clears only the exact revision durably accepted, and scopes browser-session drafts to a stable opaque workspace identity that changes across roots (`2026-09-16-dashboard-g1d-build-contract.md:10-13,25-28`). These rules close the earlier wireframe's unsupported follow-up-delivery promise.

5. **Existing UI behavior is retained rather than re-labelled as new capability.** Fleet already persists theme and notification-deduplication state and emits browser notifications for newly open operator actions (`data/fleet/fleet.js:8-9,287-305,772-780`). The amended contract preserves those keys, keeps Fleet as the default until opt-in, and distinguishes existing needs-attention alerts from any future completion notification (`2026-09-16-dashboard-g1d-build-contract.md:12,20`). It also correctly treats dry-run mode, verified evidence, writable-session eligibility, and execution capability as separate axes (`2026-09-16-dashboard-g1d-build-contract.md:14`).
