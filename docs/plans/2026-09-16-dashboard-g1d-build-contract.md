## Review findings to resolve

1. P2 has a missing execution dependency. `LiveStageDispatcher` also forbids tools/file access, and the closed builder schema only accepts a short proposal string. `docs/design/governed-change-transaction.md` explicitly documents the unimplemented application transaction. Existing run creation is not a file-editing engine. P2 needs a separately reviewed execution/workspace/transaction implementation; no new UI may claim it exists.
2. The Working wireframe promises queued follow-up delivery without a queue contract. In this increment follow-ups remain unsent drafts, with explicit manual Send once ready. No silent submission on turn completion.
3. Provider `--no-session-persistence` does not mean TORQ cannot continue discussion: `chat_runtime.py` reconstructs a prompt from signed history. Distinguish discussion continuation from build continuation.
4. Fleet already supports open-action browser notifications. Reuse them; distinguish completion notifications from existing needs-attention alerts.
5. Draft persistence cannot be claimed while using memory-only storage. In this increment use explicitly labelled browser-session drafts, scoped to run/root identity, with Clear draft, quota/storage failure handling, and no automatic evidence insertion. Do not store auth tokens, keys, attachments, or filesystem paths in browser storage.
6. Correct the earlier claim that demo dry runs cannot be verified/certified. An isolated `execute_demo` experiment returned `mode=dry_run`, receipt verification `verified`, and an existing run certificate. Mode, trust, writable-session eligibility, and execution capability are separate axes. A sample-view policy must not be presented as a cryptographic impossibility. The sandbox initially refused multiprocessing pipe creation; the approved no-provider retry succeeded.

## Executable increment

Deliver the friendly entry/workspace and truthful capability foundation (bounded P0/P1), plus a documented lifecycle assessment. Full P2/P3 remain tracked requirements, not delivered by this increment.

- Keep the legacy Fleet view as the initial default. Add an obvious Workspace/Fleet switch; only new Workspace localStorage state is the view preference (retain existing Fleet theme and notification-deduplication keys). Workspace is a polished responsive conversation-first view using existing bundled vanilla HTML/CSS/JS. Keep the original useful Fleet controls and evidence details reachable. No framework migration.
- Add authenticated, read-only workspace metadata (e.g. `GET /api/v1/workspace`) giving root kind (individual run, collection, empty/missing, unavailable), safe run identities, selected identity, actual discussion capabilities, and structured reason/remediation. No raw absolute paths, secrets, receipt bodies, or untrusted HTML in metadata. `can_start_task=false`, execution unsupported, and no decorative Build/Accept buttons pretending otherwise.
- A collection must show a clear choose-run state and safe identifiers. For this slice, give a concrete supported launch instruction with a relative run ID if runtime rebinding is not implemented. Do not switch mutable controllers by changing a projector path; preserve the existing per-run ownership/session invariant. CLI should explicitly diagnose collection roots when chat is requested, rather than mint keys for a parent collection. No arbitrary automatic newest-run selection.
- Root classification and receipt/certificate trust preflight must occur before `FileRunKeyStore.get_or_create_run_keys` or any chat identity/journal creation. Collection, missing, symlink/reparse, and untrusted roots with chat requested must fail or disable chat without key-store mutation. Metadata reads must not create keys or journals.
- Handle empty/missing/demo/untrusted/runtime-disabled/disconnected states with plain-language messages and an actionable Details/setup guidance panel. Do not classify a run as Sample by folder naming alone: use trustworthy run mode or label unknown. Do not classify every nonempty directory as a collection; bounded discovery of immediate `run-*` directories, reject symlink/reparse targets, no recursion.
- Derive attachment support from actual configured provider on the server. Claude: zero attachments; generic/no metadata defaults closed. Other supported adapters retain their existing limits. UI help, accept types, and disabled state match. Server remains authoritative on submission.
- Keep textarea editable while unavailable/working. Submission checks runtime readiness and active turn in handler, not merely disabled button. Draft text entered during an active turn must survive snapshots/completion. Do not queue or auto-send. Support Ctrl/Cmd+Enter; no accidental Enter submit.
- Drafts: browser-session storage, run/root-scoped using an opaque server identifier. Keep local unsent content separate from accepted chat content. Clear only the exact submitted revision after confirmed acceptance, preserving edits typed during request flight. Storage failure must state that the draft is only held in this tab. Preserve draft on error/expired session/reconnect. Empty-root draft cannot silently become a different run's instructions.
- The opaque `workspace_id` must remain stable for the same classified root across reload/reconnect within the browser session and differ across roots. Do not expose the raw path in it. Tests must demonstrate this stability and separation, not simply a random ID per request.
- Workspace should show the task/run title if verified; otherwise a neutral welcome. Suggestion chips insert editable prompts. Progress/usage/status comes from existing evidence; do not invent step counts, file diffs, cost, checks, or success. Raw finding remains available under Details.
- Safe visual hierarchy: project/task header, central conversation or empty state, nearby composer, concise next-action card, collapsible run details. Friendly sentence-case copy, restrained color, responsive at 320px, 200% zoom, visible keyboard focus, reduced motion, polite announcements. Keep legacy mode available.
- Add clear setup/help and README instructions explaining how to launch an individual run and what discussion can/cannot do. The existing untracked personal launcher is not a distributable product artifact: do not overwrite it. If a supported launcher is needed, add it under scripts with no hardcoded machine paths/model and never kill an unrelated port owner.
